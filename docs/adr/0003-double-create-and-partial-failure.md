# ADR 0003: 二重作成の防止と、作成後にレコードへ書けなかったときの復旧

- 状態: 採用
- 日付: 2026-10-29

## 背景

「作成」は2つの書き込みからなる: GitHub に Issue を作る(POST)と、その結果をレコードに書く(PUT)。それぞれ失敗しうるし、同じレコードを別のタブや別の人が同時に開いていることもある。

起こりうる問題:

1. 同じレコードから Issue が2つ作られる(二重作成)
2. GitHub には作れたが、レコードに番号が書けない。番号がどこにも残らず、次に押すとまた作られる

## 決定

**二重作成の防止。** 「作成済みかどうか」の唯一の判定は、レコードの Issue 番号フィールドが空かどうかとする。ボタン押下の直後にレコードを取り直し(`GET /k/v1/record`)、番号が入っていれば作成せずに画面を再読み込みする。画面を開いたときの値ではなく、押した瞬間の値で判断する。

**部分失敗の復旧。** POST が成功して PUT が失敗したら、画面に Issue の URL を表示し、「レコードへの書き込みを再試行」ボタンで PUT だけをやり直せるようにする。再試行は同じ `Issue` オブジェクトを使うので、GitHub は再度呼ばない。

## 検討した他の案

**GitHub 側で重複を探す(タイトルや本文に埋めたレコード ID で検索してから作る)。** 二重作成をより確実に防げるが、検索 API の呼び出しが毎回増え、検索の反映遅延で結局すれ違う。レコード側を正とする方が単純で、kintone の更新履歴にも残る。

**冪等キーを使う。** GitHub の Issues API には冪等キーの仕組みがないため不可。

**PUT の失敗時に Issue を閉じて(または削除して)やり直す。** GitHub の Issue は API で削除できず、閉じると通知が飛んで混乱する。作った事実を残して復旧させる方が、利用者にとって状況が分かりやすい。

## 結果

- 押下の瞬間に再取得するので、別タブで先に作られたケースは防げる。完全な同時押下(数百ミリ秒差)は防げない。GitHub 側の二重作成が起きたら、利用者が片方を閉じる
- 復旧ボタンはページを離れると消える。離れた場合は、GitHub の Issue 一覧から番号を調べ、手で番号フィールドに入れれば同じ状態に戻る(README の制限に記載)
- 処理中はボタンを押せなくし、スピナーを出す
